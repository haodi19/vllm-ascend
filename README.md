## MoE 卸载：LRC C++ 迁移实验

本开发分支研究 MoE 专家权重卸载：部分权重保存在 CPU，推理时按需加载到 NPU，
通过缓存和预取减少等待。本轮将缓存策略 LRC 的 `observe`（更新访问记录）和
`choose_victims`（选择淘汰专家）迁移到可选 C++ 扩展，保留 Python 版本用于对照。
`_update_weights` 外围逻辑、`load_submit` 和 TorchCopy 传输仍使用原实现；
本轮未启用融合规划、ACL 实验或 C++ 加载提交实验。

以下为 **2026-10-14 绿区实测（lrc_compare_03，NPU 1）**，替代此前结果。
变化率为 `(C++ / Python - 1)`，负值表示耗时降低。
`total` 为回调内部总耗时；`outer = total - observe - choose_victims - synchronize`，
其中包含 `load_submit`，各行不能直接相加。
“本轮 C++ 迁移”指该项实现是否直接迁移；“部分”表示汇总指标包含已迁移的 LRC，
并非整个过程都已 C++ 化。耗时变化不等于该项代码发生了修改。

### 单测对比

合成权重场景：256 个专家、24 个缓存槽、top-k=6、1 行 token 输入。
每轮预热 1000 次、测量 10000 次，按 Python → C++ → C++ → Python 运行，
表中为每种后端两轮的平均值，单位 **μs/次回调**。单测关闭 debug 和 profiler。

| 指标 | Python | C++ | 耗时变化 | 本轮 C++ 迁移 |
| --- | ---: | ---: | ---: | --- |
| `observe` | 7.361 | 2.023 | −72.5% | 是 |
| `choose_victims` | 25.848 | 2.686 | −89.6% | 是 |
| `synchronize` | 212.584 | 214.173 | +0.7% | 否 |
| `outer` | 86.017 | 81.310 | −5.5% | 否 |
| `load_submit`（包含在 outer 内） | 59.573 | 57.008 | −4.3% | 否 |
| `host_without_sync`（total 减同步等待） | 119.225 | 86.019 | −27.9% | 部分：包含 LRC |
| `total` | 331.809 | 300.192 | −9.5% | 部分：包含 LRC |

### 实际推理对比

沿用 [script/test_graph2.sh](script/test_graph2.sh) 的 DeepSeek-V4-Flash 单卡配置，
开启 MTP（2 个 speculative tokens）、预取、debug 和 profiler。
两组在同一张 NPU 上分别启动服务，各先发送 3 个请求预热（不计入统计），再测量 10 个请求，
固定提示词、temperature=0、max_tokens=5。
请求预热与专家预取是两个概念：`expert_prefetch_num=1` 表示每次为目标层最多预取
1 个尚未驻留的预测专家，不是预热请求数。当前层加载根据实际路由补齐当前计算所需权重，
预取则提前加载预测下一层可能使用的权重，以减少后续等待。
两组均记录 860 次当前层加载（3 行 token）和 840 次预取（1 行 token），
当前层平均加载专家数 Python/C++ 为 4.026/4.017，预取均为 0.885；回调无错误、无丢弃。

下表为平均耗时，单位 **μs/次回调**。

| 指标 | 当前层 Python | 当前层 C++ | 预取 Python | 预取 C++ | 本轮 C++ 迁移 |
| --- | ---: | ---: | ---: | ---: | --- |
| `observe` | 33.864 | 6.738 | 0.000 | 0.000 | 是；预取不调用 |
| `choose_victims` | 21.836 | 5.594 | 33.113 | 6.100 | 是 |
| `synchronize` | 886.293 | 889.069 | 211.666 | 214.202 | 否 |
| `outer` | 576.135 | 562.642 | 316.359 | 312.500 | 否 |
| `load_submit`（包含在 outer 内） | 293.907 | 285.108 | 89.457 | 85.509 | 否 |
| `host_without_sync` | 631.836 | 574.974 | 349.472 | 318.601 | 部分：包含 LRC |
| `total` | 1518.129 | 1464.043 | 561.138 | 532.803 | 部分：包含 LRC |

| 请求整体指标 | Python | C++ | 耗时变化 | 本轮 C++ 迁移 |
| --- | ---: | ---: | ---: | --- |
| 平均请求时延（ms） | 3328.732 | 3263.122 | −1.97% | 部分：包含 LRC |

请求时延从客户端发送一次 `/v1/completions` 到收到完整回复计时；`total` 则是一次
`_update_weights` 回调的平均耗时，不包含整次请求的所有层计算、生成步骤与服务调度。

### 简要结论

- **再次验证 LRC 迁移有效**：单测两函数合计耗时降低约 85.8%；实际推理当前层 LRC
  合计降低约 77.9%，预取的淘汰选择降低约 81.6%。本轮 token usage 和生成文本哈希均一致。
- **本轮观察到整体时延改善**：单测总耗时降低约 9.5%，实际当前层/预取回调总耗时
  分别降低约 3.6%/5.0%，平均请求时延降低约 **1.97%（65.61 ms）**。
  扣除同步等待后，当前层/预取回调耗时分别降低约 9.0%/8.8%。
- 回调分项中，LRC 减时是总耗时下降的主要组成；未迁移外围本轮也更快，同步等待略慢。
  “未迁移”不等于其耗时变化已证明与迁移无关；这两组顺序运行、各 10 个请求且开启
  debug/profiler，不能把整体改善全部归因于 LRC，也不能视为已验证的无采集生产收益。
- 两组计时和对比完整保存；profile 停止均超时，清理服务后成功继续测试，profile 标记为不完整。

实验入口为 [script/run_verified_cpp_tests.py](script/run_verified_cpp_tests.py)，
执行方式与字段说明见 [实验说明](docs/verified_cpp_comparison.md)。

## Overview

vLLM Ascend (`vllm-ascend`) is a community maintained hardware plugin for running vLLM seamlessly on the Ascend NPU.

It is the recommended approach for supporting the Ascend backend within the vLLM community. It adheres to the principles outlined in the [[RFC]: Hardware pluggable](https://github.com/vllm-project/vllm/issues/11162), providing a hardware-pluggable interface that decouples the integration of the Ascend NPU with vLLM.

By using vLLM Ascend plugin, popular open-source models, including Transformer-like, Mixture-of-Experts (MoE), Embedding, Multi-modal LLMs can run seamlessly on the Ascend NPU.

For detailed information on supported models and features, please refer to the [support matrix](https://docs.vllm.ai/projects/ascend/en/latest/user_guide/support_matrix/).

## Prerequisites

- Hardware: Atlas 800I A2 Inference series, Atlas A2 Training series, Atlas 800I A3 Inference series, Atlas A3 Training series, Atlas 300I Duo (Experimental)
- OS: Linux
- Software:
    - Python >= 3.10, < 3.13
    - CANN == 9.0.1 (For Ascend HDK version, please refer to the [Release Notes](https://www.hiascend.com/document/detail/zh/canncommercial/900/releasenote/releasenote_0000.html))
    - PyTorch == 2.10.0, torch-npu == 2.10.0.post2
    - vLLM (the same version as vllm-ascend)

## Branch

vllm-ascend has a main branch and a dev branch.

- **main**: main branch, corresponds to the vLLM main branch, and is continuously monitored for quality through Ascend CI.
- **releases/vX.Y.Z**: development branch, created alongside new releases of vLLM. For example, `releases/v0.13.0` is the dev branch for vLLM `v0.13.0` version.

Below are the maintained branches:

| Branch           | Status       | Note                                 |
|------------------|--------------|--------------------------------------|
| main             | Maintained   | CI commitment for vLLM main branch and vLLM v0.26.0 tag |
| releases/v0.13.0 | Maintained   | Only bug fixes are allowed, and no new release tags anymore. |
| releases/v0.18.0 | Maintained   | CI commitment for vLLM 0.18.0 version |
| releases/v0.23.0 | Maintained   | CI commitment for vLLM 0.23.0 version |
| rfc/<feature-name> | Maintained   | [Feature branches](https://docs.vllm.ai/projects/ascend/en/latest/community/versioning_policy.html#feature-branches) for collaboration |

Please refer to [Versioning policy](https://docs.vllm.ai/projects/ascend/en/latest/community/versioning_policy.html) for more details.
