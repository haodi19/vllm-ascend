# 从已有实验提取内存与 MoE 配置

四组实验的 `summary.txt` 用于性能比较，通常不包含完整启动阶段的显存统计。
`script/read_moe_run_facts.py` 读取同一实验目录中的 `run_details.log` 和四组服务日志，
将必要信息输出到控制台。不导入 Torch、不初始化 NPU、不启动模型、不写结果文件。

```bash
python -B script/read_moe_run_facts.py /实际实验目录/moe_four_way_01
```

脚本提取以下信息：

- 实际 `Effective serve command` 中的模型路径、并行规模、内存比例、图捕获配置、
  MTP 配置和专家卸载配置，不用当前 `test_graph2.sh` 代替历史配置。
- 各组 `Actual usage`、`Current KV cache memory`、KV token 容量、Prefill 专家池与层数。
- 已有 Decode 加载统计，以及最后若干条推测解码接受情况、抢占或重算日志。
- 模型路径下当前 `config.json` 的专家数、Top-K、层数与量化配置。

不存在的记录标为 `MISSING`，不从其他机器的历史数值推算。
模型配置文件是当前读取结果，不保证它在实验后未被修改。

## 读取口径

`Actual usage` 中的 weights 是框架报告的模型加载内存统计，
不能直接当成磁盘权重文件大小；peak activation 是启动阶段测量值。
KV cache 优先记录日志中的当前值，不把日志建议的 `--kv-cache-memory` 数字当成实际值。
Available KV cache memory 是预算信息，可同时保留用于解释初始化过程。

Decode 汇总和接受率日志可能覆盖预热、独立请求计时及采集阶段，
不能直接当成仅一个 profile 请求的统计。没有抢占日志也不证明绝对没有抢占。
只有逐步、逐层的原始记录才能精确回答每一步每层的加载量；总加载次数除以回调次数
只能得到该采集范围内的平均值。同一专家重复加载会重复计数。

## 显存容量与回调次数

专家缓存槽位数由配置控制，不会只因物理 HBM 变小就自动改成另一个槽位数。
在模型、输入、路由行数、图执行轮数和卸载配置相同的情况下，物理 HBM 容量变小
不直接增加回调次数。缓存未命中主要改变一次回调中的专家加载数量。

显存不足可能通过 KV 容量、调度、抢占重算等路径间接改变执行过程；
缓存配置变化也可能改变卸载路径。因此要先核对实际启动参数和执行日志。
MTP 下相同的最终输出 token 数不保证相同的执行轮数，接受情况不同可能需要更多轮。
图捕获尺寸及 padding 也使回调中的 token 行数不能简单等同于接受的 token 数。

对于按需回调从 86 次变为 129 次的记录，如果本次确认仍有 43 个相关层，
`86=43×2`、`129=43×3` 提示完整层执行轮数可能从两轮变为三轮。
这是待验证线索，不能仅凭计数确定发生了额外解码、重算或采集范围变化。
