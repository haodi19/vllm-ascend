# 搬运准备与回调间隔定位

> 历史文档副本：2026-10-29 从 `D:\华为\nano2\vllm-ascend\docs` 复制。
> 本文描述原工作树的性能诊断，所列脚本、数据和适配路径不保证存在于当前 worker-poll 分支。
> 阅读用途是理解两处性能退化及已做过的分析，不要求照搬命令重新运行。
> 当前阻塞证据与待执行实验见[交接文档](moe_mte_block_handoff_20261029_zh.md)。

对照基线是原回调版。MTE 路径后来加入的 CPU 重排、Storage 视图和缓存属于兼容措施，
减少这些措施的成本不能直接证明相对回调版有收益。目前不能把它们称为阻塞根因修复。

需要同时解决 `load_prepare` 增长和两个 `host_callback` 之间的间隔增长。
MEMCPY 之间的空隙包含这些阶段，但它们不能简单全部相加：存在多流重叠和其他计算。

## 使用已有采集定位

在仓库根目录运行以下只读命令，不启动模型、不重新解析 CANN 原始数据、不写结果文件：

```bash
python -B script/diagnose_moe_transfer_gaps.py bench_results_tmp/moe_debug_04/profile
```

脚本流式读取完整时间线，分别报告预取、按需的 `load_prepare` 和 `copy_submit`，
以及同层预取到按需、相邻层按需到预取的回调间隔。时间单位是微秒。
这些阶段计时含采集开销，性能对照仍以实验汇总中的无 profiler 窗口为准。

仅在设备时间线上存在唯一时间候选时，进一步拆分 MTE 回调间隔：

- `completion_to_wait_exit_us`：Python 回调结束到设备等待算子退出，包含原生工作线程
  发布完成、内存可见性及等待算子退出，不能直接解释为纯同步时间。
- `after_wait_to_publish_us`：等待算子退出到下一发布算子开始，需要结合映射写回、
  流间事件、路由回传及主流计算判断。
- `publish_us`：下一发布算子的执行时间。
- `publish_exit_to_callback_us`：发布结束到下一 Python 回调开始，涉及请求发现、
  工作线程调度、GIL 和 Python 入口，不能直接解释为纯 GIL 时间。

时间候选不等于关联 ID 证明的因果关系。多候选、区间重叠或设备命名不匹配时不强行拆分。
原回调版没有 MTE 发布和等待算子，因此只提供回调间隔基线及间隔内设备任务。
输出还列出最长间隔中的设备任务，辅助在 MindStudio 按时间戳核对。

本脚本用于确定修改位置，没有改变搬运路径，也没有宣称两个长时延问题已经修复。

## 等待结束点不在间隔内时

`moe_debug_04` 的 MTE 时间线能找到发布算子，但选定回调间隔内没有等待算子的结束点。
这不表示等待耗时为零，也不能据此判定是 CPU 线程或设备等待导致退化。
脚本现在独立报告 `before_publish_us`、`publish_duration_us`、`after_publish_us`，
三者在同一组有效样本上相加等于回调间隔；不再因等待匹配失败而丢弃发布边界。

`NEIGHBOR` 输出附近交接算子的起止时间，零点为前一个回调结束时刻。
负值表示在该时刻之前，不代表负耗时；这些仅是邻近事件，不能当作已确认的依赖。
`NON_WAIT` 单独展示间隔内非等待任务，防止其他空闲流的长等待覆盖全部输出位置。
`PREPARATION` 将准备与量化适配子项按回调次数归一化，避免混淆每专家和每回调计时。

## 本次结果与设备并行隔离实验

`moe_debug_04` 中每回调准备耗时，预取为回调版 37.344 μs、MTE 版 106.468 μs；
按需为 138.572 μs、512.859 μs。MTE 的量化适配分别占 54.598 μs、299.633 μs。
这是新增兼容路径的实测成本，含细项打点开销，且两组载入专家数量略有差异。
不能将减少这部分额外成本描述为相对原回调版的权重搬运优化。

预取到按需的间隔内，发布前为 347.155 μs，发布算子约 1.837 μs，发布后为
114.878 μs。这是导出坐标中的分段，不是已经校准的跨 CPU/NPU 唤醒计时。
邻近等待算子结束点落在 CPU 回调结束前约 87～95 μs；若关联正确，这与
“回调返回后才发布完成”的代码协议矛盾。必须核查时钟对齐及事件关联，不能
据此声称 CPU 轮询耗时 115 μs，更不能通过随意平移时间线来制造正值。

间隔中也能看到主流模型计算。当前 MTE 路径在预取发布后立即提交常驻 AIV 等待，
而原回调版不占用这个 AIV。它是否影响其他流计算的资源调度，目前是待验证假设。

```bash
python -B script/probe_mte_compute_overlap.py --npu 4
```

脚本使用已有 MTE 库，不编译、不加载模型、不写 profile；分别在独立子进程测试
原回调、只发布不启动等待、发布并启动等待三组。CPU 回调故意休眠 100 ms，释放 GIL；
在回调已经开始后，重放另一张独立计算图，检查其是否在回调返回之前完成。
每组运行三轮，子进程超时 90 秒即停止后续测试。

`OVERLAP_CONFIRMED` 是实际观察到并行；`NO_OVERLAP_OBSERVED` 不是死锁或资源冲突的
自动判定。需要结合 `submit_ms`、`compute_wait_ms` 及另外两组作判断。
这是对指定设备、算子和独立图调度的隔离实验，不是实际模型图的根因证明或性能验收。
本实验不改变模型的搬运、映射、等待顺序，不取消推理中的完成检查。

## 继续追查实际 Tensor 拷贝与图内间隔

独立图实验三组均观察到了重叠，包括 MTE 等待组。因此“常驻 AIV 一定阻塞其他流”
不能成立为本问题的解释。该结果不等于所有模型算子与单张图内部依赖都已排除。

进一步核对 [torch-npu v2.10.0 的 CopyKernelOpApi.cpp](https://github.com/Ascend/pytorch/blob/v2.10.0/torch_npu/csrc/aten/ops/op_api/CopyKernelOpApi.cpp)：
`copy_h2d_baseformat_opapi` 在目标不连续时创建连续临时张量，执行 H2D 后再调用
`copy_d2d_baseformat_opapi`，后者提交 `aclnnInplaceCopy`。
因此原始 scale 的 Tensor 拷贝可能包括设备布局转换，不能仅按 MEMCPY 理解。
公开版本源码与绿区开发版二进制可能有差异，这条源码路径尚不是实际阻塞点的原生栈证据。

现有日志已将复现位置缩小到预取 layer=1 的 `w13_weight_scale`：w13/w2 完成，
scale 拷贝返回后加载流同步不返回。之前只有 Python 栈，无法确定底层提交队列、
runtime 等待与设备操作之间的具体依赖。Storage 适配绕开这条路径，不代表根因已修复。

在容器已安装 gdb 的前提下，运行：

```bash
python -B script/diagnose_mte_tensor_stall.py --npu 7 --profile bench_results_tmp/moe_debug_04/profile
```

一个命令先分析已有 MTE 时间线的纯设备时钟区间，再启动一次原始 Tensor 拷贝复现。
没有 gdb 时在启动模型前退出。卡住时由独立监督进程自动附加本次启动的 engine，
抓取原生线程栈；拒绝附加非本次进程的后代。gdb 最多运行 20 秒，然后原有复现程序
继续按其超时与清理逻辑退出。不要将抓栈期间的数据用于性能对比。

关键输出保存在打印的 `diagnosis.txt`，完整原生栈和服务日志保留在绿区；只需返回
经过检查的该汇总文本。未卡住或 gdb 没有抓到栈都会明确报告，不会将其当作根因结论。

纯设备统计中，`work_during_wait_us` 表示下一发布所在流的计算候选在当前等待期间
的时间覆盖；`work_after_wait_us` 是当前等待退出到下一发布开始之间的计算覆盖；
`other_after_wait_us` 是剩余覆盖。均采用区间并集，避免重复累计重叠任务。
这能区分实际计算和非计算区间，但剩余部分不能自动命名为 CPU 轮询开销。
回调间隔变大本身也不证明整层变慢：预取完成提前、计算重叠位置变化都会改变该间隔。

### moe_debug_04 的纯设备结果

该采集来自 Prefill 布局修复后的 prepacked 版本，不是当前原始 Tensor 拷贝复现。
流 21→23 的 84 个区间中，等待退出到下一发布平均 439.253 μs，计算候选覆盖
421.265 μs（约 95.9%），其余 17.988 μs。等待期间，流 23 另有平均 518.098 μs
计算覆盖。这支持该版本存在实际计算重叠，不能把 439 μs 全称为 MTE 同步空泡，
也不能把剩余 18 μs 直接命名为 CPU 轮询成本。流 23→21 的设备间隔平均 28.095 μs。
单独的 23→23 样本不纳入这两组层间交接结论。

新启动的原始 Tensor 复现若只返回 `Engine core initialization failed`，应读取已有
服务日志首个 engine 错误，不能猜测为拷贝死锁、显存不足或机器故障。只读命令：

```bash
python -B script/diagnose_mte_tensor_stall.py --read-log bench_results_tmp/mte_native_6ce42b09
```

该命令不调用 gdb、不启动模型、不写文件。监督脚本后续运行失败也会自动保留首错，
不再只输出 API 进程的最终失败包装栈。

### 对照问题尚未闭合

MTE 间隔中存在计算覆盖，只说明该区间的组成，尚未解释为什么回调版同方向间隔更短。
不能据此将 MTE 的新增间隔视为合理开销或宣布该问题解决。后续仍以回调版为基线，
追查 MTE 修改是否改变预取完成位置、主流计算推进及按需回调开始时机。

只读对照将三个相邻 CPU 区间串起来：上层按需结束、下一层预取、该层按需。
分别统计前间隔、预取本体、后间隔、按需本体，以及到按需开始/结束的累计时间。
三元组按层号、token 行数组合和样本数量对齐；不将跨设备时钟差混入该对照。
短日志不再按错误关键词过滤，避免漏掉无 traceback 或无错误关键词的原生失败。

```bash
python -B script/diagnose_mte_tensor_stall.py --read-log bench_results_tmp/mte_native_6ce42b09 --profile bench_results_tmp/moe_debug_04/profile
```

该命令合并输出完整短启动日志和已有两组 profile 的 CPU 区间对照，不占用 NPU。
旧 profile 对照仅适用于旧版本，不能与本次原始 Tensor 复现作为同一配置的实验数据混合。
