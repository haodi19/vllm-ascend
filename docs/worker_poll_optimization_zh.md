# 基于阻塞旧版的 worker 轮询改造

## 代码基线与分支

从 `942868dd8cec9019dee04bee038bfcd678b6d66a` 新建
`dev/moeoffload-worker-poll`，不合入原开发分支中的布局适配、CPU 重排、活跃槽位前缀扫描。
原 `dev/moeoffload` 和旧版阻塞复现目录保留。

第一阶段增加可选的 `Session.configure_polling(idle_mode, timing)`，必须在 start 前调用。
默认 `yield`、计时关闭；MoE dispatcher 未调用此接口，因此原阻塞路径保持旧行为。
`spin` 仅取消空闲整轮扫描后的主动 yield，不删除 mutex，不更改 GIL、共享内存协议或设备算子。
后续去锁、直接定位槽位、绑核分别作为独立改动，不在本轮混入。

## 计时范围

worker 内使用 steady_clock，记录有界样本，停止后读取；不逐轮打印，也不在运行中读样本。
每次任务记录领取锁等待、发现任务到获取 GIL 前、GIL 获取、回调、GIL 释放、完成锁等待及完成发布。
空闲扫描每 1024 轮抽样一次，记录整轮扫描、其中的锁获取时间，以及 yield 调用前后时间。
样本容量各 8192；任务样本溢出禁止性能比较；空闲样本截断会显式报告。

计时开启时每槽位读取时钟会扰动扫描，必须与关闭计时的两组对照。
空闲样本包含初始化、图捕获、预热和逐次正确性校验间隙，不能作为 NPU 发布到 CPU 发现的时延。
spin 模式的 idle_action 主要是空计时开销。原始样本使用纳秒，输出统计统一转换为微秒，
指标名以 `_us` 结尾并标记 `unit=us`。

## 一次执行的实验

```bash
python -B script/run_worker_poll_tests.py --npu 7
```

脚本构建 Host 扩展和原设备算子，先执行 CPU 生命周期及新策略测试，再比较：

- 槽位数 1 与 2048，活动任务均放在最后一个槽位，每组内部只有 yield/spin 不同。
- 计时关闭与开启，每组交替顺序运行两轮，每轮预热 20 次、测量 200 次。
- 每次图重放均核对回调次数和 generation，失败立即停止，不重试或忽略失败样本。

单次完整交接包含 NPU 发布、CPU 空 Python 回调和 NPU 有界等待，不搬专家权重，
不加载模型、不采集 profiler，因此不触发已知 scale 搬运阻塞。
NPU Event 区间是包含图执行的完整机制区间，不是纯共享内存通知成本。
Host replay 到同步返回的时间还包含提交与等待；两者不与 worker 子项直接相加。
分项用于定位，收益以计时关闭组为主；不据此宣称真实 MoE 获得同等收益。
当前尚未加入 worker CPU 占用、上下文切换统计或严格的 NPU 发布到 CPU 发现计时。

输出保存在新建的 `bench_results/worker_poll_<编号>/summary.txt`，详细子进程日志留在同目录。
只返回 summary 内容即可。脚本不含 Git 操作，也不修改生产默认配置。

## 分项改造与验证记录

本节记录独立的改造项，避免把观测工具的开销与优化收益混在一起。当前已实现 worker 内部计时、
可选取消 yield 两项；减少扫描、减少热路径 mutex、绑核尚未实现。生产 MoE 路径仍保留原行为，
以下通过的测试不代表旧版量化参数搬运阻塞已经解决。

### 一、增加 worker 内部计时：用于定位，不是提速

#### 原逻辑与改动逻辑

原来的 C++ 工作线程启动后，循环扫描 Session 的全部交接槽位。每检查一个槽位，先获取 mutex，
读取 request generation 并判断这一代任务是否已经结束；没有新任务就继续检查下一个槽位。
发现新任务后，标记任务运行中、释放 mutex，获取 GIL（执行 Python 所需的解释器锁），
调用这个槽位注册的 Python 函数。函数返回后释放 GIL，再获取 mutex，发布 done generation
或错误状态。一整轮扫描没有执行任务时，调用 `std::this_thread::yield()`，然后开始下一轮。

原逻辑没有上述阶段的独立计时，外部只能测到整个交接区间。此次增加
`Session.configure_polling(idle_mode, timing)` 方法，在启动工作线程前配置计时开关；
默认关闭。计时开启时，在原流程的边界读取 C++ 单调时钟，记录样本，停止工作线程后再汇总输出，
不在热路径逐条打印。没有改变 generation 协议、锁的保护范围或 Python 任务的执行顺序。

| 输出字段 | 计时边界及含义 |
| --- | --- |
| `claim_lock_wait_us` | 本次发现任务的槽位，从获取领取锁之前到获取锁之后；不含此前扫描其他槽位的时间 |
| `found_to_gil_us` | 领取任务并离开锁区之后，到开始获取 GIL 之前的少量准备时间 |
| `gil_wait_us` | 获取 GIL 的整个调用区间，包含获取操作本身及可能的等待 |
| `callback_us` | 获取 GIL 后到调用 Python 函数并完成异常处理之后，包含 C++/Python 调用包装 |
| `gil_release_us` | 回调计时结束到 GIL 作用域退出后的时间 |
| `completion_lock_wait_us` | GIL 作用域退出后，到获取完成状态锁之后 |
| `completion_publish_us` | 获取完成状态锁后，到写入成功或错误状态之后；不含随后解锁、通知及样本保存 |
| `scan_us` | 抽样的空闲整轮扫描时间 |
| `scan_lock_wait_us` | 同一抽样轮中各槽位获取锁区间的累计值，是扫描时间的一部分 |
| `idle_action_us` | 整轮无任务后执行 yield 的区间；spin 模式下主要是空计时成本 |

任务样本按 generation 去掉首次执行及预热阶段，只统计正式测量的 200 次任务。
空闲样本每 1024 轮扫描抽样一次，且只有抽中的一轮没有执行任务才保存，覆盖整个 Session 生命周期。
因此空闲样本不是与每个请求一一对应的“唤醒耗时”。这些子项也不能直接相加得到完整 NPU 交接时间：
设备执行、尚未发现任务的扫描等待，以及部分通知与记录动作不在任务子项中。

#### 当前测试方法

`script/run_worker_poll_tests.py` 先构建 Host 扩展和 MTE 算子，执行生命周期与轮询配置测试，
再用独立子进程进行图重放测试，不加载模型、不搬运权重、不启用 profiler。
一次图内交接的顺序如下：

1. NPU 发布算子把本轮 request generation 写入注册的 CPU 控制内存。
2. CPU 工作线程扫描到新 generation，获取 GIL，执行一个只更新计数并记录短区间的 Python 函数。
3. CPU 工作线程发布 done generation，NPU 等待算子读到完成值后继续。

测试先执行一次普通交接，捕获上述设备流程并确认捕获未额外执行任务，再预热重放 20 次，
正式测量 200 次，因此每个成功子进程的 `callback_count` 为 221。每次重放后检查回调次数和
设备 generation 等状态；正确性读取在外部计时区间之外，但可能影响下一轮的运行状态。

测试分别分配 1 个和 2048 个槽位，全部注册任务，只有最后一个槽位收到设备请求；
其他槽位若误执行会报错。这用于观察扫描容量的影响，不是在模拟 2048 个并发请求。
旧接口要求全部槽位注册后才能授权设备访问，提交 `926fe412` 修正了测试脚本此前只注册末槽的遗漏。

每个槽位数分别测试内部计时关闭和开启，每种配置运行两轮：第一轮 yield 后 spin，
第二轮 spin 后 yield，减少固定执行顺序带来的偏差。外部仍始终记录：

- `event_interval`：同一 NPU 流上，图重放前后两个 Event 的时间差，包含发布、Host 处理、
  设备等待等，以及该区间内可能的设备空闲，不是纯内存通知时间。
- `replay_sync_host`：CPU 发起图重放到结束 Event 同步返回的墙钟时间，包含提交和等待。
- `callback_body`：Python 函数内部短代码段的时间，比 C++ 侧 `callback_us` 的范围更小。

#### 当前测试结果

2026-10-27 的单槽记录来自 `worker_poll_320046f0`，补齐的 2048 槽记录来自
`worker_poll_eed4d083`。后者 18 项生命周期测试、4 项轮询测试及全部 8 个设备测试组通过。

2048 槽开启内部计时的四个子进程中，各项均值范围如下，单位均为 μs：

| 项目 | 四组均值的范围 |
| --- | ---: |
| 领取任务时获取 mutex | 0.022～0.023 |
| 发现任务后到获取 GIL 前 | 0.018～0.019 |
| 获取 GIL | 0.575～0.906 |
| C++ 侧回调区间 | 2.894～3.953 |
| 释放 GIL | 3.348～3.833 |
| 获取完成状态锁 | 0.023～0.024 |
| 发布完成状态 | 0.019～0.020 |

这些数据没有显示轻量回调中存在数百微秒的 GIL 或单次锁等待，但不能代表真实模型执行时的竞争情况。
单次锁获取成本低，也不能说明扫描 2048 次的累计锁操作成本可以忽略。

多槽组的 `idle` 为 `{}`，表示没有收集到满足抽样条件的空闲轮次，**不表示扫描或 yield 耗时为零**。
当前数据不能单独给出多槽整轮扫描的实测均值。此前单槽抽样中 yield 区间均值约
0.105～0.125 μs，spin 对应空区间约 0.018～0.019 μs，只说明当时被抽到的调用成本。

逐槽读取时钟明显扰动多槽扫描：2048 槽的事件区间均值，yield 从计时关闭时的 35.584 μs
变为开启时的 60.440 μs，spin 从 34.493 μs 变为 55.838 μs。
开启组的中位数也从关闭组约 35～37 μs 上升至约 51～57 μs，因此不只是极端值拉高均值。
具体差值仍包含各子进程运行波动，不能全部精确归因给读时钟本身。
后续收益判断必须使用计时关闭组，开启组只辅助定位。

### 二、取消空闲 yield：已实现，暂未证实稳定显著收益

#### 原逻辑与改动逻辑

原工作线程只有在整轮扫描没有执行任何任务时才调用 `std::this_thread::yield()`；
并非每检查一个槽位就 yield，也不是每个任务执行结束后必定 yield。
yield 主动向调度器让出运行机会，是否真的发生线程切换取决于当时调度状态。

新增 `idle_mode="spin"` 后，仅跳过这个 yield 调用，立即进入下一轮扫描。
逐槽 mutex、全槽扫描、获取和释放 GIL、完成通知、MTE 发布与等待算子全部保留。
因此不能将这一改动描述成“删除所有系统调用或中断”。持续忙轮询也可能增加 CPU 占用，
本轮没有测量其 CPU 使用率和调度切换次数。默认仍为 yield。

#### 当前测试方法

使用上一小节的相同图、槽位、回调函数和测量次数，只改变 yield/spin。
内部计时关闭的两组作为收益比较；内部计时开启的两组作为辅助诊断，不能混算。
每种模式每轮 200 个样本，两轮均值按相同样本数汇总；表中 P95 是两轮各自 P95 的平均，
不是合并 400 个样本重新计算的 P95。

#### 当前测试结果

2048 槽、内部计时关闭，单位 μs：

| 指标 | yield | spin | spin − yield |
| --- | ---: | ---: | ---: |
| 事件区间均值 | 35.584 | 34.493 | -1.090 |
| 事件区间 P95 的两轮平均 | 40.629 | 40.314 | -0.315 |
| Host 重放及同步均值 | 60.569 | 59.440 | -1.129 |
| Host 重放及同步 P95 的两轮平均 | 67.130 | 66.705 | -0.425 |

事件区间均值下降约 3.1%，但第一轮下降 2.086 μs，第二轮仅下降 0.094 μs；
Host 区间第二轮还从 60.549 μs 增至 60.808 μs。现有样本只支持“观察到小幅平均改善”，
不足以认定有稳定显著收益，更不能解释或消除真实 MoE 的约 400 μs 间隔。

此前单槽、内部计时关闭时，yield 两轮事件区间中位数为 22.67、22.15 μs，
spin 为 22.84、21.25 μs，同样没有稳定的大幅变化；两种模式均出现约 1.8 ms 的长尾。
单槽与多槽分两次运行，不能直接把二者差值认定为纯扫描开销，但多槽常见区间升至
约 35～37 μs，支持下一步把扫描范围作为独立变量验证。

### 三、减少扫描范围或直接定位任务槽位：待实现

#### 原逻辑与计划改动

原逻辑扫描全部容量，不论该槽位是否会在本张图中收到请求。一个任务节点的槽位虽然固定，
但多层模型及不同捕获图可能使用不同槽位，因此不能直接让唯一工作线程永远只看一个槽位。

计划先独立验证只扫描已注册、可能发布请求的任务槽位，保留逐槽 mutex、yield 和 generation 协议。
若进一步改成直接定位下一任务，需要明确任务槽位编号如何发布、多个图与预取/按需任务如何排序，
属于另一层协议改动，不能用单槽测试替代其正确性验证。

#### 测试方法与当前结果

当前脚本只比较分配容量为 1 和 2048 的原始扫描，还没有实现同一容量下“全槽扫描/缩小扫描范围”的对照。
后续应在相同容量、相同设备请求序列下单独切换扫描策略，并增加多个非相邻槽位交替发布的正确性测试，
确认不会遗漏任务或重复执行。收益比较关闭内部计时，保持 yield、锁和绑核设置一致。
当前无该改动的收益数据。

### 四、减少热路径 mutex：待实现

#### 原逻辑与计划改动

原逻辑每检查一个槽位就加锁，即使没有任务也会执行锁操作；任务完成发布状态时再次加锁。
锁同时涉及生命周期和 Host 侧操作的保护，不能直接删除全部 mutex。

计划单独设计工作线程对 request/done 的原子读取与状态发布，利用运行期间任务注册表不变的约束，
减少空闲扫描中的锁操作，同时保留注册、启动、停止、资源释放等管理路径的必要互斥。
必须核对 Host 提交、错误发布和退出取消之间的数据竞争，明确内存可见性后才能实现。

#### 测试方法与当前结果

后续固定扫描策略、yield 模式与 CPU 亲和性，只切换热路径锁实现，比较计时关闭的交接区间。
除正常重放外，还需回归停止/超时、未完成请求、回调异常、资源释放及跨线程操作。
当前测得的约 0.02 μs 单次获取锁区间不等于整轮累计锁开销，也不是去锁后的预期收益；
本项尚未修改，无收益结果。

### 五、工作线程绑核：待实现

#### 原逻辑与计划改动

当前没有为工作线程设置单独的 CPU 亲和性，线程可在进程允许的 CPU 集合内由操作系统调度。
计划增加可选的工作线程绑核，限制其在指定 CPU 上运行，尝试减少迁移和调度波动；
只绑定工作线程，避免误把模型提交线程等其他线程都限制到同一 CPU。
指定 CPU 必须属于容器允许集合，绑核也不等于独占该 CPU。

#### 测试方法与当前结果

后续固定 yield、锁和扫描实现，对照不绑核与绑核；记录实际允许 CPU、绑定结果和时延分布，
同时检查提交线程与工作线程是否争用同一 CPU。优先单独验证，再考虑与 spin 组合。
当前没有实现或测试绑核，无收益结果。

### 当前阶段结论

轮询开关及计时工具已通过独立 CPU/NPU 测试。去掉 yield 尚未显示稳定显著收益，
多槽逐项计时有明显扰动，不能拿开启组作为性能结论。下一项优先独立验证扫描范围，
再判断是否需要减少累计锁操作和绑核；暂不据这些轻量测试改变真实 MoE 默认行为。
权重搬运阻塞与轮询开销仍是两个问题，本轮没有运行权重搬运，不能宣称前者已经修复。
