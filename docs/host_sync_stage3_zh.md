# 本地 CPU/NPU 交接扩展：第三阶段

第二阶段已验证普通执行中的 MTE 标记交接。第三阶段检验相同发布、等待算子能否
捕获成图，以及每次重放是否产生新的请求并等待对应的 CPU 任务完成。
本阶段代码已准备，真实图执行结果仍待绿区验证。

## 测试流程

1. 自动构建独立扩展并复跑第二阶段检查，保留普通执行的回归验证。
2. 在单独的子进程中新建一个非默认 NPU 流，分配固定地址的设备状态与注册 Host 内存。
3. 普通执行一次正常交接作为预热，generation 从 0 变为 1。
4. 使用 `torch.npu.graph` 在该流捕获发布、等待两个原生算子。捕获前后检查设备状态与
   CPU 回调次数保持不变，防止把捕获时执行误认为图重放。
5. 每轮只调用 `graph.replay()`，不再调用两个原生 launch 包装函数，也不由 Host 写请求
   generation。NPU 发布算子递增 generation，CPU 工作线程处理新任务，NPU 等待完成。
6. 每轮同步流并检查结果。全部结束后销毁图，再释放设备访问权限、停止工作线程、释放内存。

图固定的是算子和地址。generation 位于设备内存中，每次执行发布算子都会重新读取、
递增，因此图不需要为每轮重新捕获。CPU 回调由常驻工作线程通过请求标记触发，
不作为 `_launch_host_func` 节点加入图。

普通图测试默认重放 100 次，加上预热，共产生 101 个请求；预期最终结果的 generation
和 observed_generation 都为 101，CPU 回调次数也为 101。
异常和轮询上限各运行一个独立子进程：先正常预热一次，再重放一次，预期 generation 为 2，
code 分别为 2 和 3。异常不会被当作成功，达到轮询上限也不会放行真实模型计算。

## 绿区执行

更新代码后，在容器的项目根目录执行：

```bash
python -B script/run_host_sync_stage3.py --npu 1
```

`--npu` 指定物理卡号；`--rounds` 指定正常测试的重放次数，默认 100。
`--cann-root`、`--soc-version` 与第二阶段一致。
默认每次在 `build/host_sync_device_stage3/run_<唯一编号>` 中重新构建，路径显示在控制台。
这样避免复用 CANN 增量构建的中间文件，旧目录和已成功的动态库不会删除。
`--build-dir` 可指定精确目录；重新构建时应使用新的空目录。
仅复用成功产物时使用 `--skip-build --build-dir <成功输出中的构建目录>`。
单独使用 `--skip-build` 则沿用第二阶段的 `build/host_sync_device_stage2`。
脚本自动复跑普通执行与图执行两组检查，输出直接显示在控制台，不含 Git 操作。
只产生必要构建产物，不写实验结果文件。请返回 `CAPTURE PASS`、各项 `RESULT` 和
`STAGE 3 SUMMARY`；出错时返回失败步骤及其报错。

## 验证边界

本阶段仍是独立扩展实验，不修改 MoE manager、原来的 `_launch_host_func`、LRC 或推理脚本。
捕获范围只有两个原生算子，不含混合 Torch 算子、专家权重搬运或多槽任务；CPU 测试回调
只做请求检查。这些接入条件不能用本阶段结果代替验证。

每轮同步并读取结果是正确性校验，并非性能计时方式。暂不比较同步开销、不保存 profile。
图正确性通过后，再设计 `_launch_host_func` 对照、时延计量与 profile，避免把未通过验证
的图路径作为性能基线。等待有轮询上限，子进程有超时保护；图或设备同步失败后仍按
第二阶段的隔离进程退出策略处理，不提前释放可能被设备使用的内存。

首次绿区第三阶段执行通过了 18 项 Host 单测和 10 项校验，但复用第二阶段目录时，
CANN 的 `ld.lld` 对已有 `.o` 报 `unknown file type`，测试停在构建阶段。
该结果不说明图捕获失败，因为尚未运行图测试。由于相同算子此前已构建并通过第二阶段，
目前先采用独立新目录排除增量构建产物的影响；具体中间文件为何不可识别尚未确认。

接口依据：[torch_npu 2.10 图捕获与重放实现](https://github.com/Ascend/pytorch/blob/v2.10.0/torch_npu/npu/graphs.py)。
