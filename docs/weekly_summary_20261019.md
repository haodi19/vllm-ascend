# MoE 卸载周总结（2026-10-19）

## 1. LRC 策略 C++ 迁移与验证

完成 `observe` 和 `choose_victims` 的 C++ 扩展迁移，保持原算法，保留 Python 版本用于对照。
权重加载提交和同步逻辑仍使用原实现。10 月 14 日单卡测试结果如下：

| 指标 | Python | C++ | 耗时降低 |
| --- | ---: | ---: | ---: |
| 单测 LRC 两函数合计（μs） | 33.209 | 4.709 | 85.8% |
| 单测 `_update_weights` 总耗时（μs） | 331.809 | 300.192 | 9.5% |
| 实际推理当前层 LRC 合计（μs） | 55.700 | 12.332 | 77.9% |
| 实际推理预取 `choose_victims`（μs） | 33.113 | 6.100 | 81.6% |
| 平均请求时延（ms） | 3328.732 | 3263.122 | 1.97% |

迁移有效降低了 LRC 计算开销，两组生成文本哈希及 token usage 一致。
实际推理沿用 `test_graph2.sh`，开启 debug/profiler，各测量 10 个请求；
请求整体时延下降是本轮观察结果，尚不能全部归因于 LRC，也不代表无采集场景的生产收益。

## 2. MSTX 可视化与时延定位

为 `_update_weights`、LRC、加载提交、同步等待及 Python 回调外层添加 MSTX 标记，
在 MindStudio 中与 NPU 传输时间线对齐，并细分 CPU 外围处理。

可视化观察到，`observe` 与 `choose_victims` 之间的 `gap_debug` 耗时较大，约 **200 μs**。
该阶段包含调试信息整理、排序、张量格式化及日志输出，属于 CPU 外围开销；
该数值是所观察区段的耗时，不作为所有回调的平均值。
后续通过关闭 debug 对照，确认其对回调总耗时和设备空泡的影响。

## 3. `_launch_host_func` 原理整理与优化讨论

结合 torch_npu 2.10.0 源码梳理图捕获/重放和 CPU/NPU 协同流程，形成
[中文流程文档](moe_offload_cpu_npu_flow_zh.md)。
`_launch_host_func` 经由 `aclrtLaunchCallback` 安排阻塞式回调：报告处理线程获取 GIL，
执行 `_update_weights_guarded` / `_update_weights`；回调完成后，指定流的后续设备任务继续。
这不是将 NPU 程序迁移到 CPU，而是设备流与 CPU 回调线程之间的通知、执行及同步。

下一步重点分解预取与按需回调之间的空隙，区分传输、事件依赖、报告调度和 GIL 等待。
目前已补充回调外层标记及间隔分析；底层调度/GIL 开销仍需进一步独立测量，
尚不能将约 100 μs 的回调间隔全部归为 `_launch_host_func` 开销。
在明确主要耗时后，再评估替代同步方案，保持路由、权重和槽位映射的一致性。
