# MTE 改造与两处退化的因果复核

## 本次证据边界

`moe_debug_04` 是 Prefill 布局修复后的 prepacked 版本，包含量化 Storage 适配，尚未
验证后续视图缓存提交的性能。新运行 `mte_native_6ce42b09` 使用原始 Tensor 拷贝，
在加载 checkpoint 的 41/46 分片时退出，没有模型加载完成、MTE dispatcher 启用或
预取拷贝检查点记录。该失败不能认作之前的 scale 拷贝阻塞再次复现。
主机剩余 RAM 不能排除容器内存限制，但没有退出信号或内核记录时也不能直接判为 OOM。

## 按提交顺序核对改造

| 改动 | 提交 | 与问题的关系 |
| --- | --- | --- |
| 将按需、预取 ACL 回调替换为发布/等待 AIV 算子及一个 CPU polling worker | `74762b1a` | 改变执行线程、通知和设备等待节点；是最初的交接差异 |
| 加载流从普通 Stream 改为 SyncLaunchStream | `be7b674d` | 改变 Host 提交方式；换流后原始 scale 拷贝仍曾阻塞，不能称为完整修复 |
| 量化参数通过 Storage 适配，处理稠密转置布局 | `5f647839`、`1953c5da` | 为绕过原始 Tensor 路径而加；产生准备、检查、视图和重排开销 |
| CPU scale 按目标布局预打包 | `387c6d14` | 避免 Decode 每次重排，但保留 Storage 适配 |
| 缩小 worker 扫描范围、分离无 profiler 计时 | `682ccde7` | 未改变层间 join 或完成条件；不能据此确认剩余 gap 原因 |
| Prefill 池对齐 scale 布局 | `81ad9284` | 修复预打包方案的 Prefill 消费路径；发生在原始拷贝阻塞之后 |
| 复用已验证视图 | `644db18e` | 进一步减少适配成本的尝试；不是阻塞根因修复，也不属于旧 profile 的数据 |

比较接入前与当前 manager，预取的 ready event、映射写回、完成事件记录及按需的
wait_event 位置未改；改变的是这些事件之间的交接实现及加载路径。不能仅因 Python
事件调用位置相同就认定底层图调度相同，但应优先隔离新增交接与加载差异。

## 两个问题分别能确认什么

### 准备开销与原始拷贝阻塞

旧 profile 每次预取的 load_prepare 从 37.344 增至 106.468 μs，其中新增适配占
54.598 μs；按需从 138.572 增至 512.859 μs，其中适配占 299.633 μs。
这些是新增兼容路径的成本，含打点扰动。它们不能解释更早发生的原始 Tensor 拷贝阻塞。

历史逐任务日志定位到预取 layer=1：w13、w2 完成，w13_weight_scale 的 copy_ 返回后，
加载流 synchronize 不返回。公开 torch-npu 2.10 源码显示非连续目标的 Tensor 拷贝
可能生成连续临时张量、H2D 和设备侧 InplaceCopy。哪条流、事件或执行上下文造成阻塞，
尚无原生栈证据，因此不能宣布重排或 Storage 是必需操作。

### 预取到按需间隔

同为 84 个三元组，按层号和 token 行数组合对齐后，以前一层按需结束为零点：

| CPU 时间区间，μs | callback | MTE | 差值 |
| --- | ---: | ---: | ---: |
| 到预取开始 | 100.938 | 55.673 | -45.265 |
| 预取本体 | 442.378 | 494.890 | +52.512 |
| 预取结束到按需开始 | 120.021 | 463.863 | +343.842 |
| 到按需开始，累计 | 663.336 | 1014.426 | +351.089 |
| 到按需结束，累计 | 2035.592 | 2696.804 | +661.211 |

预取结束位置仅晚约 7.247 μs，但下一按需开始晚约 351.089 μs。因此，不能用
“预取提前结束，使空隙看起来更大”解释这组均值。增长仍主要集中在预取之后。
两组加载专家数和采集扰动未完全一致，这不是净性能收益验收。

设备时间线显示后续区间有约 421 μs 计算覆盖，只解释区间组成；没有回答为什么
回调版的重叠更好或推进更快。独立图加法实验也只排除了“AIV 等待必然阻止所有其他流”。
尚不能排除具体模型算子、图调度与执行上下文的相互作用。

## 只替换预取交接的诊断开关

新增 `host_sync_prefetch_callback=false`，仅允许 MTE 后端显式开启。开启后：

- 预取使用原 `_launch_host_func` 和报告线程，完成语义与原回调版一致。
- 按需仍使用 MTE 发布/等待及其 worker。
- 加载流、权重布局、量化拷贝方式、预取预测、映射及 join 位置均由原配置决定，不随开关变化。
- 默认关闭，原回调版和正常 MTE 版行为保持不变。这是因果定位用的混合路径，不是最终优化方案。

原始 Tensor 拷贝的单次诊断命令：

```bash
python -B script/diagnose_mte_tensor_stall.py --npu 7 --prefetch-handoff callback
```

脚本保留逐任务诊断、原生抓栈和失败清理；报告线程中的拷贝停滞也能触发抓栈。
初始化早退会额外输出容器可见内存限制与计数，并尝试读取本次 engine PID 的内核记录。
只有实际到达对应拷贝并完成，才能用于与历史阻塞位置比较；启动失败无因果判定价值。

若混合路径完成原始量化拷贝，支持问题与预取交接实现或其执行线程上下文有关，
削弱“SyncLaunchStream 加这个布局必然失败”的解释，但还需同版本全 MTE 对照复核。
若仍卡在同一处，则不能把问题仅归因于预取 MTE 等待节点；应检查共同的加载流和转换路径。
该串行逐任务诊断不用于评价 host_callback 间隔性能。

功能确认后，可在真实对照入口使用 `--prefetch-handoff callback`，保持同一 quant-copy
配置与版本，关闭逐任务诊断，比较全 MTE 和混合路径的间隔。不能拿新混合路径结果
直接与旧 prepacked profile 混合计算收益。最终是否能撤掉适配或恢复回调版时延，尚待这些证据。

## 第一轮结果与合并的第二轮

当前版本两次原始 Tensor 诊断中，仅预取恢复回调的 `mte_native_077b3621` 完成推理，
全 MTE 的 `mte_native_cbca8e66` 则在请求执行时停滞。后者捕获到原生线程栈：
MTE worker 经 `NPUStream::synchronize`、`aclrtSynchronizeStreamWithTimeoutImpl` 等函数
等待设备完成；主线程经 `NPUEvent::synchronize` 等待事件。此时不是 Python 准备计算
或 LRC 函数占住 worker。runtime 内部缺少符号，尚未证明具体设备依赖环。

全 MTE 输出的前八批拷贝在捕获前预热阶段已经完成，不能把这些 COMPLETE 解释为
停滞时那次图内加载也完成。诊断计数已修正为仅在 MTE/混合路径的真实回调中消耗，
不让 eager 预热耗尽检查额度。正常计时关闭该诊断，不增加逐任务同步。

第二轮最多启动三次模型，统一使用当前提交：

1. 原回调，原始量化拷贝。
2. 全 MTE，prepacked 量化拷贝。
3. 仅预取恢复回调、按需仍 MTE，使用与第 2 组相同的 prepacked 拷贝。

第 2、3 组只改变预取交接；第 1 组提供目标基线，不能把其与第 2 组差异全归因于交接。
每组预热 1 请求、关闭 profiler/MSTX 进行 3 请求分项计时，再采集 1 请求 profile。
三组均不启用逐任务拷贝诊断，自动检查输出和 token 用量、比较搬运分项与同层 CPU 三元组。
失败即停止，不自动追加重跑；profile 不完整时明确报告间隔对照不可用。

```bash
python -B script/run_mte_prefetch_comparison.py --npu 7
```

仅需返回打印的汇总 `summary.txt`，各组详细日志、JSON 数据和 profile 留在绿区。
本轮属于既定三轮计划的第二轮，不再单独要求逐组执行与逐组返回输出。
若混合路径同时恢复间隔而加载计时基本一致，支持新增间隔来自预取交接组合；
若间隔不恢复，就不能将量化阻塞与间隔退化强行归为同一原因。

## 第二轮结果与最后两组验收（2026-10-27）

`prefetch_compare_0cd11967` 三组输出一致、profile 完整。同层/token 行数配对的
84 个 CPU 三元组中，预取结束到按需开始的间隔为原回调 107.943 μs、全 MTE
467.964 μs、混合交接 78.658 μs。两组 MTE 使用相同 prepacked 搬运，说明预取
交接组合是间隔增大的直接影响因素；尚未分离设备等待节点和执行线程上下文的作用。

不能把间隔减少的 389.307 μs 作为净收益：混合版预取前间隔、预取函数体、按需函数体
分别增加 97.869、128.140、132.089 μs。以前一个按需结束为起点，到下一个按需结束
仅缩短 31.208 μs（2410.250 → 2379.042），仍高于原回调的 2169.057 μs。
这些是含 profiler 扰动的区间，不能作为无采集性能结论。

无 profiler 计时中，全 MTE/混合版的按需加载专家总数均为 1340，load_prepare
为 201.588/194.052 μs，load_submit 为 460.918/446.291 μs。恢复预取回调并没有
消除额外适配开销。原回调对应值为 143.887/304.659 μs，但专家总数为 1294，不能
把均值差全归因于单次拷贝变慢。预取专家数均为 236；原回调/全 MTE 的 load_submit
为 73.302/124.914 μs，而 load_submit 加等待为 321.274/313.037 μs，提交和等待
之间存在时间重新分配。

最后一轮最多两次模型启动：原回调与混合交接均走原始 Tensor 拷贝，关闭额外布局适配
和逐任务同步。此前混合原始拷贝只在诊断同步开启时通过，本轮补齐正常执行验证。

```bash
python -B script/run_mte_prefetch_comparison.py --npu 7 --original-copy-final
```

本轮同时输出正确性、搬运计时、间隔和 profile。若通过，可判断混合交接是否是无需
额外适配的可用退路；它仍保留预取回调，不能称为全 MTE 修复。若失败或仍明显退化，
按既定边界停止追加模型试验，保留结果并回到 `942868dd8cec9019dee04bee038bfcd678b6d66a`
建立独立定位分支。当前证据能定位到预取交接组合，不能声称已证明 runtime 内部依赖环。
